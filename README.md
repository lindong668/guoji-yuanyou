## 二、★ 与 3 号的依赖关系（3 号要不要改？）

### 结论：**3 号不用改。**

| 数据 | 来源 | 靠 3 号吗 |
|---|---|---|
| 布伦特 / WTI 实时价 | `/api/oil-live` — 8 源链路 | **主要不靠**，`site3` 只是兜底之一 |
| 黄金实时价 | 前端 4 源 + `/api/gold-live` 7 源 | **主要不靠**，3 号是兜底 |
| **国内油价（各省 92/95/98）** | `getMarket()` → 3 号 `/data` 带 `X-Access-Key` | **必须靠 3 号** |
| 汇率换算 | `open.er-api.com` 主 + `frankfurter.dev` 备 | **完全不靠 3 号** |

### 为什么 3 号不用改

1. `/data` 接口结构没变，2 号仍以同样方式（带 `X-Access-Key`）读取
2. 密钥与 3 号一致，未改动
3. 新增的兜底调用只在**主源全挂时**才轮到 3 号，负载可忽略

### ⚠️ 但有一件事要盯

国内油价是 **3 号 cron 定时抓**（每天 08:30 Asia/Shanghai）。
如果 3 号的定时任务挂了或额度耗尽，国内油价会显示旧值且**页面不会报错**。
所以 3 号仍需保持正常运行 —— 它现在是国内油价的**唯一来源**。

## 二之一·补、★ 法语首页标题被劈成"四行"（本次再修）

上一轮修复引入的新问题：法语首页卡片标题被拆成三四行，非常难看。

```
根因一：.ttl 写了 overflow-wrap:break-word —— 允许在【单词内部】断开。
        法语 "Pétrole brut Brent" 被劈成 Pétro / le / Brent …，行数暴涨。

根因二：首页徽标用的是完整文案，法语
        "En direct · Mis à jour il y a 14s" 有 30+ 字符，
        与 19 字符的长标题挤在窄卡片里必然换行。

修法：
  .card h3 .ttl   overflow-wrap:normal + word-break:normal
                  → 只在【词与词之间】换行，单词保持完整，最多折两行
  .card h3 .ttl   flex:0 1 auto（不强制伸展，可收缩吸收剩余变化）
  首页徽标         改为【精简文案】：「实时 · 14s」
                  去掉 "Mis à jour il y a" 这类前后缀，长度砍掉一半以上
  详情页           空间宽裕，仍用完整文案（不改）

domtest 实测首页徽标渲染结果：
  修复前  [En direct · Mis à jour il y a 0s]
  修复后  [En direct · 0s]

⚠️ 局限：jsdom 不做布局计算，"几行"必须浏览器目测确认。

## 二之二、★ 徽标随秒数上下跳（本次修复）

现象（法语首页 + 浏览器翻译为中文时最明显）：

```
秒数是个位数 → 徽标在标题右边
秒数变两位数 → 徽标整块掉到下一行
```

```
根因：上一轮为解决"长语言徽标被挤掉"，给 .card h3 加了 flex-wrap:wrap。
      徽标宽度会随位数变化（4s→14s 多一个字符），
      宽度刚好跨过阈值时就被挤到第二行 —— 于是随着秒数跳动反复上下跳。

修法（不再让徽标换行，改为让【标题】吸收宽度变化）：
      .card h3        flex-wrap:nowrap   整行永不换行，徽标始终留在标题同一行
      .card h3 .ttl   flex:1 1 auto + overflow-wrap:break-word
                      标题包进 .ttl，空间不够时由它收缩/内部换行
      .live-dot .ago  min-width:3ch
                      锁住最长形态（14s / 59s / 10m 都是 3ch），
                      一位变两位时徽标宽度不变 → 标题不用重排 → 卡片高度不跳

代价：一位数时秒数右侧最多多留约 1 个字符（0.7rem 下 ≈6px），
远小于之前 3.2ch 留白 + 双重 flex gap 造成的那种明显"分开"。

⚠️ 顺带修了一个测试假阳性：CSS 断言没剥注释，
   注释里写的"之前用 flex-wrap:wrap"被正则命中，
   规则已改成 nowrap 测试却仍报通过。现在所有 CSS 断言先 stripCss() 再匹配。

⚠️ 局限：jsdom 不做布局计算，"不再跳行"需在浏览器目测确认
   （法语首页开浏览器翻译，盯 10 秒以上）。
```

## 二之三、★ 原油开休市判断（本次新增）

之前只有黄金有休市判断，原油没有 —— 休市时也显示「实时 · Ns 前更新」，
而实际抓到的是休市前的沿用值，与当初黄金的问题一模一样。

### 时段（IANA 时区名，冬令时自动跟随）

| 品种 | 时区 | 交易时段 | 每日休市 |
|---|---|---|---|
| 布伦特 | `Europe/London` | 01:00–23:00 | 23:00–01:00 |
| WTI | `America/New_York` | 周日 18:00 → 周五 17:00 | 17:00–18:00 |

### ★ 休市定格规则（曾写反过，别再改回"休市就不抓"）

```
休市时【抓一次】/api/oil-live，拿到市场最后一笔成交价（收盘价）
  → 写入后就【不再轮询】，数字从此定格不动
  → 徽标显示「休市中」，不跳秒
```

**为什么不能"休市就不抓"**：那样首页会用 `/api/oil-live` 的值、
详情页会留服务端值（3号），**两个页面显示不同数字**
（用户实测：总览 110.56 vs 详情页 114.19）。

统一成"两边都取同一个接口"，一致性才有保证。
已加真实测试：冻结到"布伦特休市、WTI 开市"的时刻，
同时加载总览页与详情页，比对两边数字必须相同。

### ★★★ 开休市判定：只看"价格有没有在动"（用户拍板的方案）

**为什么彻底弃用交易所排程**：我们的源是券商 CFD（biquote），近乎全天报价，
ICE 官方时段（伦敦 01:00–23:00）跟它对不上 ——
于是出现"明明价格在跳，却显示休市中"。**排程不可靠，实测才可靠。**

| 条件 | 结论 |
|---|---|
| 价格有变动（2 分钟内变动过） | **实时** |
| 连续 2 分钟（约 8 轮 × 15s）完全没动 | **休市中** |

一有变动**立刻**翻回实时，无需等待。

真实测试（可推进时钟，6 场景全过）：

```
场景1 排程休市 但价格在动        → 实时     ← 之前的 bug 场景
场景2 价格冻结 >2 分钟           → 休市中
场景3 排程【开市】但价格冻结      → 休市中   ← 证明不再盲信排程
场景4 冻结未满 2 分钟            → 实时     ← 阈值边界
场景5 判定休市后又抓到变动        → 立刻翻回实时  ★ 关键
场景6 刚加载（还没观察到冻结）    → 实时
```

### ★★★★★ 来回导航跳价的【终极根因】：多实例各自缓存

**用户场景**：点布伦特进去→退出来→点 WTI 进去→退出来→点黄金进去→退出来，
来回往返时价格会跳，**而且不是刷新时刻也跳**。

**前两层已修（不够）**：
- SSR 与接口同源 ✅
- 黄金前端改走接口缓存 ✅

**但还会跳，因为**：模块级 `liveCache` 是**每个 Worker 实例各自一份**。
CF 并行跑多个实例，这次请求打到 A、下次打到 B，两份缓存各自刷新 → 值不同。

**实测（模拟两个实例）**：

```
无共享缓存   实例1 = 110.80   实例2 = 110.82   ← 不同！这正是用户看到的跳价
启用 KV      实例1 = 110.80   实例2 = 110.80   ← 完全一致
```

**修法**：缓存写进 KV，所有实例共享同一份。代码已**优雅降级**——
没绑定 KV 时自动退回模块级缓存，不会报错、不影响部署。

#### ★ KV 绑定：直接复用 3 号的 namespace（已配置好，无需新建）

多个 Worker 可以绑同一个 namespace（binding 名不同即可）。
`wrangler.toml` 已填好 3 号的 namespace id，**开箱即用、不用执行任何命令**。

```toml
[[kv_namespaces]]
binding = "PRICESCOPE_CACHE"
id = "af76a1d05d444244a468ed02d6617f98"   # ← 3 号的 namespace
```

2 号写入的 key 是 `live:v1`，与 3 号的 `oil_data` / `gold_data` /
`gold_history` / `cn_oil_data` 互不冲突，不会覆盖对方数据。

#### ★★★ KV 写入额度（关键，别调回 15 秒）

**Workers KV 免费版：1,000 次写入/天，按【账号】计算、所有 namespace 合计。**

| 共享周期 | 2 号写入/天 | 结论 |
|---|---|---|
| 15 秒 | 5,760 | ✗ 必爆 |
| 60 秒 | 1,440 | ✗ 爆 |
| 120 秒 | 720 | △ 偏紧 |
| **180 秒** | **480** | **★ 当前值** |
| 300 秒 | 288 | ○ 页面 5 分钟才变一次 |

**⚠️ 额度是与 3 号共用的**，而 3 号自己消耗不小：
黄金每 3 分钟写 2 个 key（`gold_data` + `gold_history`）≈ **960 次/天**，
加原油约 25 次 ≈ **985 次/天**，几乎已吃满 1,000。

所以：

```
当前：3号 ~985 + 2号 480 ≈ 1465/天   → 仍超出免费额度
```

**超出会怎样**：KV 写入被拒绝。代码已 try/catch 静默降级为模块级缓存，
**不会报错、不会白屏**，只是回到"跨实例可能跳价"的状态。

**建议（可选）**：优化 3 号写入频率（盘中历史 bar 只更新内存、收盘才落盘；
黄金当前价 3→5 分钟）可省约 286 次/天 → 3 号降到 ~391，加 2 号 480 ≈ 871，卡在额度内。

想彻底不纠结就升级 Workers 付费版。

### ★★★★★ 最终方案：前端价格锚定（sessionStorage）—— KV 方案已否决

**KV 方案已否决（用户拍板），`wrangler.toml` 的 `kv_namespaces` 保持注释。**

否决理由：免费版写入额度 1,000 次/天。要落进额度，就必须把刷新周期
从 15 秒放宽到 3 分钟 —— **等于把实时行情变成 3 分钟前的旧值**。
而"两个页面差 0.02"本来就是市场在这一秒里真的动了，**不是错误**。
为了消灭 0.02 的差异而牺牲数据新鲜度，是捡芝麻丢西瓜。

**替代方案（已实现）**：前端价格锚定。

```
记住"上次显示的价格 + 时刻"，15 秒内重复加载直接沿用，【不发请求】。
用户点进详情页只用 1~2 秒 → 锚点必然未过期 → 显示首页那个值 → 不动。
```

| | KV 方案 | 前端锚定 |
|---|---|---|
| 数据新鲜度 | 3 分钟旧值 ✗ | 15 秒 ✓ |
| 额度消耗 | 480 次/天 | **0** ✓ |
| 治"来回导航跳" | ✓ | ✓ |
| 治"跨用户一致" | ✓ | 不需要 |

**实测（市场 mock 成持续跳动，以此区分"不抓"与"抓了"）**：

```
有锚定   首页 110.79 → 详情 110.79（新增请求 0 次） ← 不动
无锚定   首页 110.79 → 详情 110.82（新增请求 1 次） ← 跳
```

⚠️ 该测试已【回退验证】：把 `ANCHOR_MS` 改成 0（等于没锚定）后测试立刻变红。

**锚点结构 `{v, t, mv}`**：`mv` = 最后变动时刻，必须一起存 ——
否则新页面 `lastMoveAt` 恒为 0，开休市判断会退化成排程兜底，
又会出现"排程开市但价格其实冻结"的误判。

**有效期 15 秒 = 轮询周期**：超过就正常抓新值，不会把数据变旧。

### ★★★★★★ 真正的根因：刷新不该由"打开页面"触发（用户拍板）

绕了一大圈（SSR 同源 → 源粘滞 → KV → 锚定），**真正的根因其实很简单**：

```
每个页面一加载就立刻拉一次新数据
→ 进去拉一次、出来又拉一次
→ 用户来回点就看到数字来回变
```

用户反过来问了一句点破的：**"进去看到旧数，出来拉了新数，再进去还是旧数，
这不合理吧？让来回导航不刷新不就行了？"**

**最终方案：全局节拍（global beat）。**

```
把"上次刷新时刻"存进 sessionStorage（跨页面共享）
下次刷新点 = 上次 + 15 秒 —— 【与在哪个页面无关】
· 距下次节拍还有余量 → 排个定时器等着，到点才拉
· 已过点 → 拉一次，然后按 15 秒循环
```

首页、布伦特页、WTI 页、黄金页**共用同一个节拍**。
刷新由"15 秒到了"触发，不再由"打开页面"触发。

**顺带统一**：黄金页原来是 30 秒一轮，与其它页 15 秒不一致，已统一为 15 秒。

**实测（进首页→布伦特页→回首页→黄金页，每次间隔 1~2 秒）**：

```
修复后  四个页面都是 $110.79，累计真实请求 2 次   ← 导航不再触发刷新
修复前  数字各不相同，累计真实请求 6 次
```

⚠️ 已回退验证：把 `BEAT` 改成 0（等于没有节拍）后测试立刻变红。

**踩到的两个坑（都修了）**：

1. `startBeat` 在 `beatDelay()<=0` 时又立刻 `fn()` 了一次 —— 外面已经调过 `cycle()`，
   结果首屏连抓两次（实测请求计数直接从 0 跳到 2）。现在只注册定时器，不重复抓。
2. 锚点与节拍同周期（都是 15 秒）会互相阻塞：边界处"节拍说该刷了、锚点说还不用刷"，
   结果永远不刷新。现在**锚点只对首次加载生效**，之后一律按节拍真抓。

### ★★★★★★ 锚点与节拍必须合并 —— 两套机制会打架（用户实测发现）

上一版我同时做了【锚点】和【节拍】两套独立机制，结果互相打架，暴露两个 bug：

```
bug1：beatMark() 在页面加载时【无条件】调用
      → 每次导航都把节拍往后推 15 秒
      → 用户一直点进点出，节拍永远重置，永远刷不了新数据

bug2：锚点让首屏不抓，但秒数从【旧的抓取时刻】继续走
      → 秒数一路涨到 20s、30s 才刷新
      → 用户看到"怎么 30 秒才刷一次"
```

**修法：合并成一个快照 `{v, t, mv}`，只有【真抓到数据】才更新 `t`。**

| | 秒数 | 刷新点 | 导航时 |
|---|---|---|---|
| 合并前 | 从旧 t 走 → 会涨到 30s | 每次导航 +15s → 永远推迟 | 重置 t ✗ |
| 合并后 | `now - t` 连续 | `t + 15s` 恒定 | **不动 t** ✓ |

**实测（进首页→布伦特页→回首页→黄金页，各隔 1~2 秒）**：

```
导航 4 次   四个页面都是 $110.79，真实请求 2 次   ← 数字不动
导航后 t    1793246400000（与首次抓取时刻完全相同）← 节拍没被推迟
推进 15 秒  请求 +2，t 变为 1793246415000         ← 准时刷新
```

⚠️ 已回退验证：把"导航重置 t"的旧行为改回去，测试立刻变红。

**还踩到一个坑**：`d0` 不能在异步 fetch 完成前计算 —— 那时 `t` 还是 null，
得到 `d0=0` → `setTimeout(fn,0)` 立刻又抓一轮（实测首页连抓 3 轮、6 次请求）。
现在分两种情况：`d0>0` 按剩余时间排队，`d0=0` 直接 `setInterval`。

### ★★★★★★★ 连接中断也不能随便显示 —— 跑完【第一整圈】才允许（用户要求）

用户原话：**「最起码得从头到尾跑一轮，抓不到才显示连接中断，再接着跑剩下的轮次」**。

**之前的错**：价格一冻结（原 30 秒）就立刻显示「连接中断，正在重试」，太频繁、吓人。

**现在的三段式**（休市不可能只休三五分钟，起码半小时起步，我们有充足时间确认）：

```
冻结 <60 秒                → 实时（市场本来就可能几十秒不动）
冻结 ≥60 秒，悄悄开始探测  → 仍显示实时（第一圈内【完全不吓人】）
跑完【第一整圈】仍无新值   → 才显示「连接中断，正在重试」
跑满 3 轮（8源×3次×3轮）   → 才判「休市中」
```

原油一圈 = 8 源 × 3 次 = 24 次探测（约 72 秒）；
黄金源少，一圈 = 4 源 × 3 次 = 12 次。**第一圈内用户看不出任何异常。**

### ★★★★★★ 休市判定必须多源多轮 —— 单源静默 ≠ 市场休市（用户硬性要求）

用户原话：**「判定休市是很严肃的问题，至少 99.9% 把握才能判」**。

**之前的错（很严重）**：只在一个源上观察「2 分钟没变动」就显示「休市中」。
但券商 CFD 源本身可能沿用旧值、也可能接口不稳定，**单源静默根本不等于市场休市**。
后果：明明开盘中却显示休市中，用户刷新一下又好了 —— 看着很吓人。

**现在的规则**：

| 情况 | 显示 |
|---|---|
| 抓到新数据 | **立刻开市**（有变动就是开市） |
| 价格冻结 ≥2 个节拍(30s) | **重新连接中**（进入多源探测） |
| 探测跑满仍无变动 | 才判 **休市中** |

**探测强度**（逐个源轮询，每源连续 3 次，走完一圈算 1 轮）：

```
原油 8 源 → 至少 3 轮 = 8×3×3 = 72 次（约 3.6 分钟）
黄金 4 源 → 至少 6 轮 = 4×3×6 = 72 次（源少，所以轮数加倍）
```

任一源返回新值 → 立刻开市并清零进度；**所有源 × 所有轮**都没变动才判休市。

**进度存 sessionStorage**：刷新 / 导航【不会】从头再来
（否则用户一刷新探测就重置、永远走不完 —— 用户实测到的现象）。

**实测（probetest）**：

```
探测 1 次   → 重新连接中   ✗ 不判休市
探测 41 次  → 重新连接中   ✗ 不判休市（进度 r=1,i=5）
探测 81 次  → 休市中       ✓ 跑满 3 轮才判
中途给新价  → 立刻翻回「实时 · 0s前更新」并清零进度
刷新页面    → 进度保留（不会从 r=0 重来）
源全部失败  → 也推进换源，不卡死在同一个坏源
```

⚠️ 已回退验证：把轮数改成 0（等于不探测就判休市）后，9 项里 4 项立刻变红。

**踩到的坑**：首次拿到值时 `lastVal` 还是 null，不能当成「变动」去清探测进度 ——
否则一刷新（新页面首次抓取）就会把上一页攒的轮次清零，探测永远走不完。

### ★★★★★★★ 漏拍不能假装"实时" —— 秒数封顶（用户截图实测）

用户截图：**「实时 · 20s / 28s / 29s前更新」**，且**秒数一超过 15 秒，点进详情页就归零**。

**根因**：源返回空值（0/null）时走了静默分支 —— 既不更新 `lastOk`、也不改 `state`，
于是秒数一路涨到 29s 还显示"实时"。用户此时点进详情页，详情页判定"早该刷了"
→ 立刻真抓 → `lastOk=now` → 秒数**归零**。

```
节拍 15 秒 → 秒数 >15s 【本身就证明这一拍没抓成功】
```

**修法两条**：

1. 源返回空值时【不能静默】，如实标成断线
2. `paint()` 加漏拍保护：`lastOk` 距今超过 1.5 个节拍 → 显示「连接中断」，不再假装实时

### ★★★★★★ lastOk 的语义：成功通信时刻 ≠ 价格变化时刻

**踩到的坑**：漏拍保护加上后，probetest / fixtest 各有 2 项变红 ——
因为探测时价格冻结，`lastOk` 不更新，ago 涨到 70 秒，
触发漏拍保护显示"连接中断"，与「探测第一圈内保持实时」直接冲突。

**根因是语义混淆**：

```
原逻辑  只有【价格变了】才更新 lastOk
        → 价格冻结 = 链路断了？错，链路通着，只是价格没动
正确    【拿到值】就更新 lastOk
        → 没拿到值（失败/空）才不更新 → 这才是真的漏拍
```

修完后两个逻辑不再打架：

```
链路通 + 价格冻结 → ago 小 → 第一圈保持实时 → 跑完一圈才"连接中断" → 跑满才"休市中"
链路断（失败/空值）→ ago 涨 → 立刻"连接中断"
```

### ★★★★★★ 本轮修掉的三个真 bug（都是用户实测发现的）

**① 黄金点进去秒数归零**

```
根因1  setGoldVal() 【漏写节拍快照】→ ps_tick_gold.t 一直是旧值
       → 详情页判定"该刷了" → 真抓一次 → lastOk=now → 秒数归零
根因2  markLive() 里【无条件】lastOk=Date.now()
       → 沿用快照刚恢复的秒数被立刻清零
```
修：补 `tSet('gold',...)`；`markLive` 的 lastOk 改为取自节拍快照的 t。
实测：`首页 10s → 详情 10s`（修复前是 `首页 10s → 详情 0s`）。

**② 详情页只剩一个绿点、没有秒数**

```
根因  原油详情页的探测模块【漏插】（上一版脚本中途失败未保存），
      于是 setInterval(probeTick,PGAP) 引用了不存在的函数
      → 整个脚本抛错 → 徽标再也不更新
```
修：补齐原油详情页的探测模块；`pass()` 沿用快照时补 `lastOk=a.t`。

**③ 连接中断太频繁** → 见上一节「跑完第一整圈才允许」。

⚠️ 已回退验证：把这三处修复改回原样后，fixtest 9 项里 3 项立刻变红。

### ★★★★★ 并发闸门 —— 别让"访问量大"把额度写爆（实测）

**上面 480 次/天的前提是：每 3 分钟只写一次。但没加闸门时这是假的。**

缓存过期的瞬间如果同时来了 N 个请求，**每个都会认为该自己刷新**：

```
实测（修复前，抓取耗时 300ms）
   1 并发 → KV 写入  1 次
   5 并发 → KV 写入  5 次     ✗
  20 并发 → KV 写入 20 次     ✗
  50 并发 → KV 写入 50 次     ✗ 访问量一大，480/天 变几千/天
```

**两道闸门**：

1. **单飞（inflight）**：同一实例内并发请求共享同一次抓取，不重复抓。
2. **写入前二次确认（double-check）**：抓完准备写 KV 时再看一眼，
   若别人已写了更新的就**丢弃自己的、采用别人的**，不写第二次。

```
实测（修复后）
  场景A 3 实例 × 100 并发 → KV 写入 ≤ 实例数，外部源调用不再随请求数线性增长
  场景B 50 个独立实例     → KV 写入 1 次   ★ 与访问量彻底解耦
```

⚠️ 单飞必须用 `try/finally` 释放，否则抓取抛异常会让 `inflight` 永久卡住，
之后所有请求都挂在这一次失败的刷新上（测试里有断言守着）。

### ★★★★ 来回导航跳价（用户实测场景）：黄金前端直连外部源，完全不受缓存约束

**用户场景**：点布伦特进去→退出来→点 WTI 进去→退出来→点黄金进去→退出来，
来回往返时价格会跳，**而且不是刷新时刻也跳**。

**根因（与上面那条不同，是独立 bug）**：

```
SSR        → 后端 liveOverlay()   【有 15 秒缓存】
黄金前端 JS → 直连 4 个外部源      【无缓存，每次现抓】  ← 问题在这
```

每次导航 = 新页面加载 = 前端直连现抓一次，市场在动 → 每次值都不同。
原油因为走 `/api/oil-live`（有缓存）所以没这个问题，**黄金漏改了**。

**修法**：黄金前端改为与原油统一 —— **优先走 `/api/gold-live`（同一份缓存），
失败才回退直连**。首页 `pullGold()` 与详情页 `pass()` 两处都改。

**端到端验证**（外部源 mock 成持续跳动，以此区分"走缓存"与"现抓"）：

```
修复前  首页 4030.02 → 详情 4030.06 → 首页 4030.10 → 详情 4030.14   ← 每次都不同
已修    四次全部 4030.00                                              ← 完全一致
```

⚠️ 该测试已【回退验证】过：把代码改回直连后测试立刻变红，确认不是假阳性。

### ★★★ 真·根因：SSR 与 /api 走的是【两条不同的取数路径】

**这才是"点进去跳一下、点出来又跳一下"的真正原因**，源粘滞治不了它：

```
首页/详情页 SSR   → liveOverlay()          【有 15 秒缓存】  → 值 A
前端 JS 轮询      → /api/oil-live          【直接调 getOilLive()，无缓存，每次现抓】 → 值 B
```

`/api/oil-live` 之前**绕过缓存直连源**，所以 SSR 给一个值、JS 立刻又给一个值，
页面加载完数字必然跳一下。

**修法**：不带 `?src=` 时，`/api/oil-live`、`/api/gold-live` 统一走 `liveOverlay()`——
与 SSR 是同一份缓存；只有探针显式带 `?src=` 才绕过缓存（排查时要新鲜值）。

端到端验证（真实 `worker.fetch`，且**mock 模拟市场持续跳动**）：

```
已修  首页 110.78  详情 110.78  接口 110.78   ← 三处一致
修复前 首页 110.78  接口 111.50               ← 不一致，测试立刻变红
```

⚠️ 若 mock 写死固定价，这个测试会**假阳性通过**（两边都返回同一个数）。
所以 mock 必须让价每次都变，才能区分"读缓存"与"现抓"。已按此实现并回退验证过。

### ★★ Sticky Provider（源粘滞）—— 解决"首页 102.03、点进去 102.02"

**问题**：原来每次请求都从头按序尝试源，一旦 biquote 偶发超时就落到 yahoo，
下次又回 biquote —— 两个源口径略有差异，用户看到"点进去价格跳一下、点出来又跳一下"。

**修法**：记住上次成功的源，**下次优先复用**；只有它失败了才换下一个。

```
第 1 次  biquote 成功 → 记住 biquote
第 2 次  仍用 biquote → 值与上次完全一致  ★
biquote 挂 → 自动切 yahoo
biquote 恢复 → 继续用 yahoo（不来回跳，保持稳定）
```

这样同一时间窗口内，首页 / 详情页 / 连续刷新拿到的都是同一个源的值。
真实测试 11 项全过。

### ★★★ 开休市判定：三规则（最终版，不再抖动）

**为什么改**：上一版单独用"价格动不动"判定 → 行情清淡几分钟不动就翻成休市，
一动又翻回实时，用户看到"一下实时、一下休市"，非常乱。

| 条件 | 结论 |
|---|---|
| ① 价格在动（3 分钟内有变化） | **实时** |
| ② 冻结 ≥10 分钟 **且** 排程也说休市 | **休市中** |
| ③ 其他（不动但排程开市 / 冻结未满 10 分钟） | **实时** |

**为什么不抖**：判休市要【同时】满足"冻结够久"和"排程休市"，
而排程由 IANA 时区算出、是确定的，不会来回变。
只有"真的收盘 + 价格真的停了"才会翻成休市。

真实测试（冻结时钟推进，4 场景全过）：

```
场景1 排程休市 + 价格一直在动      → 实时     ← 现在就是这个情况
场景2 排程休市 + 冻结 >10 分钟     → 休市中
场景3 排程开市 + 冻结 >10 分钟     → 实时     ← 清淡也不误判休市
场景4 动过之后只冻结 5 分钟        → 实时     ← 抗抖动关键
```

### ★ 顺带：无条件 15 秒一抓，不再节流

旧逻辑"判定休市就停止轮询、5 分钟才复查一次"是**死循环**：
判断开休市靠观察价格变动，停止轮询就永远观察不到变动 → 永远显示休市中，自己锁死自己。
已改为无条件 15 秒一抓（CF 无 Netlify 那种部署额度限制，请求成本可忽略）。

### ★★ 实测覆盖层：排程只是参考，"价格在不在动"才是真相

**用户实测发现的问题**：布伦特显示「休市中」，但数字一直在跳。

原因：ICE 官方时段是伦敦 01:00–23:00，伦敦 00:30 判休市没错；
但我们的源是**券商 CFD 链路（biquote MT5）**，它近乎全天报价。
**排程与数据源的实际行为对不上**，于是自相矛盾。

修法：

```
观察到价格在动（3 分钟内有变化）  → 认定交易中，显示"实时"
排程休市【且】价格确实不动        → 才显示"休市中"
```

这样无论交易所时段怎么改、源怎么换，显示永远与用户看到的数字一致。

真实测试（冻结到伦敦 00:30，即排程休市）：

```
场景1 价格持续在变  → 徽标 [实时 · 0s前更新]   ← 不再误判休市
场景2 价格完全不动  → 徽标 [休市中]            ← 正确显示休市
```

### ★ 顺带修了一个隐藏 bug：h24 午夜陷阱

`Intl.DateTimeFormat('en-US', { hour:'2-digit', hour12:false })`
在**午夜会返回 "24" 而不是 "00"**（en-US 默认 h24 时制）。

```
伦敦午夜 → hour = "24" → 时段判断全部错乱
```

已全部改为 `hourCycle:'h23'`，实测 en-US/en-GB 下均返回 "00"。

### 关键设计：两腿独立判断

布伦特与 WTI 时段不同，**经常一个开一个休**：

```
实测（真实执行开休市函数，冻结时刻）
  北京周四 06:00   布伦特 开市   WTI 开市
  北京周四 07:26   布伦特 休市   WTI 开市   ← 当前
  北京周六 08:00   布伦特 休市   WTI 休市
  北京周一 08:00   布伦特 休市   WTI 开市   ← 11/1 美国切冬令时后仍正确
```

所以一次请求拿到两个数，**各自独立判状态**，休市那一腿不写、显示「休市中」。

### 为什么不用 2 号实时数据做报表

2 号是 8 源动态回退，各源口径略有差异，用来累积 OHLC 会让曲线有小跳变。
**报表继续用 3 号 cron 累积（来源固定、每小时采样、口径一致）。**

### ⚠️ 两个保守处理

```
布伦特周日是否开盘，各源口径不一（ICE 官方为周日 23:00 伦敦开盘）
  → 保守按休市处理（休市时抓到的只是沿用值，抓了也白抓）

取不到时区信息（老浏览器）
  → 默认开市（宁可多抓一次，也不误显示"休市中"）
```
